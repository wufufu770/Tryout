### 抽选中被特别确认的"易错点"

这几条如果写错，会直接误导使用者的技术判断：

- **HashMap 树化阈值**：`≥8` 只是条件之一，**还需要数组容量 ≥64**。漏掉后半句是高频错误。
- **SQL 注入防御的盲区**：预编译参数化**不能**用于动态表名/列名（因为那是标识符不是值），必须用白名单。这是最常见的实践误区。
- **K8s 调度是初始决策**：不是"调度完就定了"，Pod 起来后 Kubelet 失败会触发重新调度。
- **3PC 不解决一致性问题**：它用超时缓解阻塞，一致性仍可能出问题。
- **RANK vs DENSE_RANK**：跳号与否的差别，写对了。

## 四、发现的真实问题：参考答案过长（已修复）

### 现象

| 指标 | 数值 |
|---|---|
| 超过 500 字符的题 | **226 题（28.0%）** |
| 超过 1000 字符的题 | 32 题 |
| 最长 | 1818 字符（`PyTorch:实现 RAG 检索增强`） |
| 中位数 | 335 字符 |
| 最短 | 82 字符 |

**分布高度集中：**
| 题型 | 超长题数 |
|---|---|
| coding | **126** |
| design | 46 |
| technical | 46 |
| behavioral | 8 |

coding 题超长的根因是**参考答案里塞了完整代码实现**。

### 为什么这是真问题

A1 的评估 prompt 需要同时容纳：问题 + 候选人回答 + 参考答案 + 行为锚点。**参考答案是最占位置的部分之一**。226 题（28%）超长意味着：

- 挤压了其他内容（锚点可能被稀释）
- 推高 token 成本
- 与 W4-4 的上下文治理目标冲突

### 为什么不能直接删题库内容

**题库内容本身没有错。** 完整代码对人是有价值的学习材料，站内浏览也仍然需要展示全文。

问题只在于**评估时不需要那么长** —— 评估技术深度需要的是「判分要点」，不是「完整实现」。

### 修复方案

新增 `web/src/lib/evaluation/referenceAdapter.ts`（15 例测试）：

- **在评估链路上裁剪**，不动原始题库资产
- **按句读边界截断**，不在句子/代码中间硬切（硬切会让模型看到半句代码并错误推断）
- **coding 题使用更短上限**（300 vs 500 字符）—— 代码自解释，判分靠锚点
- **抽取"判分要点"**：优先取含数字/阈值/代码标识符的句子，作为显式 hints 注入 prompt
- 英文句号带**词边界判断**，不误切小数（`0.75`）、缩写（`e.g.`）、域名

修复过程中修掉 3 个自引入的真 bug：
1. 句末标点被丢弃（`slice(0, i + 0)` 应为 `i + 1`）
2. 英文句号判定方向写反（"前面是词字符"会排除掉**所有**正常英文句号）
3. 显式 `max` 参数被 `min()` 覆盖，形同虚设

## 五、残留限制

| 项 | 说明 | 影响 |
|---|---|---|
| 未覆盖 `questions`（反问）题型 | 抽样时该题型题数少，未单列 | 该题型内容量小，评估时按行为面处理 |
| 抽样比例 | 24 / 808 = **3.0%** | 置信度有限；建议后续用社区反馈持续校正 |
| 答案未做交叉验证 | 仅我的技术判断，未与权威文档逐条比对 | 少数细节（如具体版本差异）可能有偏差 |

**建议**：把 V7 变成**持续性**检查——每新增一批题就跑一次抽样，而不是一次性验收。

## 六、给后续的提醒

1. **参考答案会越写越长。** 新增题时应遵守：参考答案控制在 500 字符内，coding 题用「判分要点 + 关键代码片段」而非完整实现。
2. **`adaptReference` 是评估链路的保护层，不是内容层的。** 题库页面仍展示全文。
3. 若将来接入题库 PR 贡献，应把「参考答案长度」列为 review 项。
